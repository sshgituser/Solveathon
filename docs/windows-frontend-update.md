# Windows: post-freeze frontend sidecar

## Что это и чего он не делает

`tools/package_frontend_update.py` создаёт небольшой ZIP **только с данными** общего фронта из указанного Git commit и применяет его к отдельной остановленной распакованной копии принятого Windows-комплекта. Крупный исходный ZIP остаётся неизменным; runtime не перекомпрессируется. Применение создаёт **новый** полный каталог и читает/копирует/проверяет runtime, поэтому это не мгновенная операция. Входные ZIP не исполняются и в них не запускаются команды.

Это не замена EXE, Python, CUDA, движка, API, весов, `windows/`, лицензий движка или Android APK. `code_commit` движка остаётся прежним; новый commit указан отдельно как `frontend_commit` в `engine-win64/manifest.json`. `START-HERE.txt` относится к исходному комплекту, а не к версии обновления. Старые результаты проверки EXE/движка не являются проверкой будущего фронта, его совместимости, камеры, UI или Android.

Сборка протокола ниже может быть проверена на уже принятом commit, но **это не поставка будущего нового фронта**: до freeze и согласования точного commit его в инструмент не передавать. Рабочее дерево намеренно игнорируется, включая незакоммиченные и неотслеживаемые файлы.

## Условия и границы

- Windows, Git в PATH, Python 3.11+; для `apply` требуется Windows. Исходный архив, обновление и обе копии хранятся приватно, вне Git. Для применения достаточно места примерно под ещё одну полную распаковку (около 3,9 GB для принятого архива), плюс запас для временных файлов. Никакого запуска/остановки/перезапуска приложение инструментом не производится.
- Получите **независимо** от владельца релиза согласованные точный commit, SHA-256 базового ZIP и SHA-256 обновления. Хэши обнаруживают расхождение, но не подтверждают личность отправителя; подписи инструмент не предоставляет. Защищайте от одновременного изменения входы и родительский каталог назначения. `--confirm-stopped` — утверждение оператора, а не проверка процессов. Не используйте рабочую установку: только свежую отдельную распаковку, никогда не запускавшуюся.
- На этапе build сравнивается настоящий SHA-256 большого ZIP, проверяется манифест движка, состав ZIP и контрольные суммы Windows; фиксируются SHA исходного манифеста и полного ZIP. Берутся точные Git-объекты только конкретного commit через `git cat-file`, без файлов рабочего дерева и архивных фильтров. Путь должен входить в allowlist: три HTML-маршрута, JS под `frontend/src/`, CSS под `frontend/styles/`, явно перечисленные публичные ассеты и их лицензии. Неподдерживаемые файлы вызывают ошибку, а не молча исчезают. Видео не включается: новый или старый MP4 в области обновления требует отдельного решения, этот инструмент откажет. `frontend/README.md` и `frontend/DESIGN.md` не обновляются.
- Все ранее упакованные обслуживаемые пути фронта и поддерживаемые публичные ассеты обязательны в новом Git-снимке. Переименование/удаление старого маршрута ведёт к отказу. Это проверка наличия файлов, **не** доказательство отсутствия битых импортов, динамических ссылок, совместимости протоколов или соответствия статического allowlist будущему backend. Особенно важно: принятый backend отдаёт только разрешённые маршруты; при необходимости нового backend-маршрута нужен согласованный новый пакет движка, а не этот sidecar.
- При apply независимые SHA обоих ZIP сверяются повторно. ZIP sidecar принимается только с фиксированным инвентарём и разрешёнными путями; все его размеры и хэши проверяются. Содержимое базовой копии целиком сверяется с привязанным манифестом и архивом, лишние файлы и ссылки/reparse points запрещены. Создаётся частный временный каталог рядом с новым назначением; каждый итоговый файл перечитывается и проверяется по ожидаемому хэшу, после чего каталог переименовывается в новое имя. При ошибке опубликованного результата нет; при аварийном завершении может остаться скрытый `.qolda-apply-*` для ручного удаления после проверки. Старый каталог и архив не изменяются. Недоверенные параллельные процессы и сбой питания во время файловых операций не считаются покрытыми гарантиями; контролируйте доступ и делайте резервные копии.

## Выпуск после freeze

Пример в PowerShell. Пути — заполнители; выбранные выходные имена ещё не должны существовать. Базовый SHA ниже относится только к зафиксированному `Qolda-Windows-Private-63137a2.zip`; другой архив требует своего независимо подтверждённого SHA.

```powershell
$repo = 'C:\PRoject\Qolda'
$base = 'C:\private\Qolda-Windows-Private-63137a2.zip'
$baseSha = '5bb058e2155a540797e443465ad4c6670e0a07375fa82708e223a5f24fde2074'
$commit = '<ПОЛНЫЙ_СОГЛАСОВАННЫЙ_GIT_COMMIT>'
$sidecar = 'C:\private\frontend-update.zip'
python "$repo\tools\package_frontend_update.py" build --ref $commit --base-zip $base --base-sha256 $baseSha --out $sidecar
```

Сохраните и передайте полученный в JSON `sha256` sidecar по отдельному доверенному каналу. Отдельно подтвердите, что выданный `frontend_commit` в точности согласован. В sidecar `update.json` содержит инвентарь и SHA каждого файла. Никакой Git-ветки как доказательства согласования недостаточно: передайте конкретный immutable commit, а не `HEAD` или имя ветки.

## Применение offline к остановленной копии

Заранее полностью распакуйте **проверенный** базовый ZIP в новый частный каталог, ничего там не запускайте и не меняйте; отсутствие файлов, добавленные файлы, записи работы приложения или другая сборка не допускаются. Храните также оригинальный ZIP рядом или на другом локальном носителе: он необходим при применении для независимой привязки. Оператор удостоверяется, что копия не работает. Команда читает её, но не редактирует; результат — другое, до этого не существовавшее имя.

```powershell
$baseCopy = 'C:\private\base-copy'
$result = 'C:\private\updated-copy'
$updateSha = '<SHA256_ИЗ_ДОВЕРЕННОГО_КАНАЛА>'
python "$repo\tools\package_frontend_update.py" apply --base-zip $base --base-sha256 $baseSha --base-dir $baseCopy --update $sidecar --update-sha256 $updateSha --frontend-commit $commit --out $result --confirm-stopped
```

При успехе JSON сообщает `verified_files`, SHA итогового манифеста, оба SHA входов и оба commit. Храните квитанцию отдельно. Только после отдельной приёмки владелец решает, как переносить/запускать новую копию; старую установку инструмент не переключает. До включения в релиз нужно проверить совместимость UI, маршруты и функции на целевой Windows-машине без сети.

## Единый ref для Android

Sidecar — **не Android APK и не Android updater**. Для Android владелец берёт тот же `frontend_commit` и проверяет SHA файлов общего фронта и публичных ассетов по `update.json` до Android-специфической интеграции. Дальше Android-сборщик размещает web-копию в `assets/web/`, сохраняет необходимую специфику entry/bridge по `android/ANDROID_BRIDGE.md`, проверяет встроенный APK и подпись. Поскольку Android entry может намеренно преобразовываться, его итоговый SHA не обязан равняться исходному: преобразование и его проверка документируются отдельно. Sidecar не проверяет и не выполняет этот шаг.

## Фактическая проверка протокола, не релиз будущего UI

На частной отдельной копии принятого ZIP `63137a2` собран и применён sidecar из **того же** commit `63137a22bef4a4ea220d753dc7b0c492d88c1387`: 64 файла фронта/ассетов, sidecar 2 271 205 байт, SHA-256 применённого sidecar `9bb790fce4cf2fbd3b67bee5170f076dd55f81d84f9311aed096c30b98384cbd`. Применение завершилось с кодом 0 и повторно проверило все 25 604 файла новой копии; SHA-256 итогового engine-манифеста `11d8bfe289f8d049cd5fe1d8871c4f91a01027233854109f3b49a1606f5f504a`. Исходный ZIP после применения сохранил подтверждённый SHA `5bb058e2155a540797e443465ad4c6670e0a07375fa82708e223a5f24fde2074`. После дополнительной изоляции Git-переменных окружения сборка повторена; инвентарь и хэши её файлов совпали с применённым sidecar. Тесты и запуск приложения не выполнялись. Это доказательство сборки/копирования/хэшей на старом commit, **не проверка изменённого фронта **.
